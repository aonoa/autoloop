# 架构文档

本文说明 Agent Autoloop 由哪些部分组成、请求如何流动、状态存在哪里，以及单机和多机部署时的边界。协议字段的权威定义见 [protocol.md](protocol.md)，状态转换见 [state-machines.md](state-machines.md)。

## 设计目标

Agent Autoloop 是一个**事件驱动、无界面、零运行时依赖**的 Agent 自动化中台。它不替 Agent 思考，也不内嵌模型调用；它负责：

1. 接收外部事件和定时事件；
2. 按可信规则决定交给哪个 Agent、在哪个目录、用什么权限；
3. 把一轮执行派给接单程序；
4. 保存事实、卡片、回执、决定和授权；
5. 在需要人决定时通过通道发卡片，收到回答后继续。

四个方向都可以替换：**来源（source）**、**Agent**、**通道（channel）**、**交付（delivery）**。内核不知道任何具体产品名，也不主动连接外部系统。

## 逻辑架构

```text
外部系统 ──HTTP/Webhook──▶ 来源插件 ──事件──▶ ┌──────────────────────────────┐
                                              │            中台               │
  人 ◀──卡片── 通道插件 ◀──卡片/通知──────────│  HTTP 门面 → 决策 → 事实日志  │
  人 ──回答──▶ 通道插件 ──回答事件──────────▶ │        ↓                      │
                                              │  投影/查询视图 → /v1/state    │
  接单程序 ◀──领活── HTTP 长轮询 ─────────────│        ↑                      │
     │                                        │  到期任务 / 定时 / 暂停 / 重试 │
     └──启动 Agent 进程──▶ Agent ──最后一条消息/回执──▶ 接单程序 ──结果──▶   │
                                              └──────────────────────────────┘
```

关键点：

- **中台不向外发请求。** 来源、接单程序、通道都主动连接中台；这样中台不需要知道对方地址，也不需要保存对方凭据。
- **Agent 是进程。** 接单程序给 Agent 一段提示词，读取它的最后一条消息。任何有打印模式、能接收提示词并输出的命令行程序都能接。
- **一轮结束，事项继续。** Agent 进程退出不代表事情结束；提问、复查和后续事件会让同一事项继续。
- **规则才是指令。** 事件里的文字是资料，不能改变交给谁、目录、权限或收件人。

## 组件边界

| 层         | 目录                            | 职责                                                              | 不应该做什么                                   |
| ---------- | ------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| 内核       | `kernel/`                       | 决策、事实追加、投影、规则匹配、到期计算、HTTP 行为、卡片表单     | 不读时钟、不取随机数、不访问网络、不知道产品名 |
| 运行外壳   | `host/`                         | Node HTTP、SQLite、文件、配置、时钟、状态汇总、服务安装、插件加载 | 不重新实现内核决策                             |
| 协议       | `protocol/`                     | 类型、JSON Schema、输入校验、HTTP 客户端、一致性检查              | 不持有业务状态                                 |
| 接单程序   | `worker/`                       | 领活、启动 Agent、心跳、停止、读取和提交回执、本地运行记录        | 不决定派工权限                                 |
| 命令       | `cli/`、`bin/`                  | 用户操作、状态展示、MCP、备份、更新、卸载                         | 不绕过 HTTP 门面的鉴权                         |
| 插件       | `plugins/`                      | 具体来源、Agent、通道、交付实现                                   | 不反向导入内核；内核不导入插件                 |
| 示例与文档 | `examples/`、`docs/`、`skills/` | 场景模板、最小插件、协议与操作说明                                | 不作为运行时依赖                               |

`tests/purity.test.ts` 守住内核与产品解耦、内核不主动连接外部等约束。新增产品接入应放在插件层。

项目登记也遵守这个分层：`host/projects.ts` 是配置控制面的唯一实现，负责同时校验和写入 `rules.json` 与可选的 Activity 项目清单；CLI 和 owner-only HTTP 门面都复用它。它不放进 InSoulForge Activity，因为 Activity 只是可选通道，项目管理在有没有 QQ 机器人时都必须存在。内核只读取规则，不接触文件；模型和插件没有配置写权限。

## 一次事件如何走完

以 GitHub 新 Issue 为例：

1. **进入。** GitHub 调用 `POST /v1/in/github`，内置 `github` 来源插件验证 HMAC 签名，把 Webhook 翻译成标准事件；也可以由可信程序用来源密钥调用 `POST /v1/events`。
2. **校验。** `protocol/validate.ts` 检查字段、长度、字符集和类型。`subject`、`link`、`actor` 只允许安全字符，因为它们可能进入提示词或参与身份比较。
3. **匹配。** 内核按 `when.source` 和 `when.types` 找出候选规则。支持精确类型、`*` 和前缀通配（如 `issues.*`）。
4. **准入。** 没有 `policy` 时，来源密钥通过即接受；`gate` 再检查来源的 `allowlist`、`admission`、`bots`；`assess` 再排一轮研判。被拒绝的事件仍记录，便于审计。
5. **确定性放置。** 没有规则命中时，先看项目的 `when.subjects` 和 `aliases`；能唯一确定就直接派发，不询问模型。
6. **调度。** 仍未放置且配置了 `policy.dispatch` 时，排一轮只读调度轮。中台把项目、节点、在线状态、活跃事项和最近轮次做成快照交给调度 Agent；它只返回 `route`。
7. **复核。** 中台重新校验项目、来源、发送人、节点、事项阶段和置信度；不通过就转成未分配卡片，不派活。
8. **排队。** 同一规则同一对象（`lane`）已有排队轮次时，事件并入该轮；`parallel` 让不同对象各自成事项。每个未分配事件独立调度，避免合并后只处理第一个。
9. **派活。** 接单程序用 `GET /v1/work` 长轮询领取任务，拿到这一轮的 Job、独立 token、资料和上下文。
10. **执行。** 接单程序在指定 `cwd` 启动 Agent，设置权限、资料文件和会话。Agent 把结果写在最后一条消息里，可附 `agent-autoloop` 回执块。
11. **回执。** 接单程序校验并提交结果；内核在同一个事务里写入轮次结果、卡片、复查、回执事件和投影。
12. **继续或结束。** 有回答、复查或新事件时，同一事项继续；否则进入空闲，不再占用 Agent 进程。

调度轮本身不写授权，也不执行工作；它只是一次控制面判断。模型不能凭记忆添加项目或节点，最终能否派活只由中台事实决定。开启 `policy.dispatch.create` 后，调度 Agent 可以提议新建项目：内核只写 `project_creations` 待办，宿主在事实提交后原子写入配置，成功再重新调度；关闭时仍生成未分配卡片，由本人通过 CLI 或 owner-only 项目接口登记。

## 事件溯源与投影

中台的事实日志是权威状态：

- `facts` 表只追加，每条事实包含序号、时间、类型和变更；
- 决策在同一事务里产生事实并更新投影，提交后才响应；
- `projections` 是索引化投影，正常启动复用；格式指纹变化时从日志逐条重建；
- `projection_refs` 记录行与事实的对应关系，`why` 用它还原一轮的时间线；
- 查询视图（`events`、`runs`、`cards` 等）在每次启动时重建，不写迁移脚本。

因此升级不需要迁移数据，旧事实不会被改写。投影损坏可以丢弃重建；事实日志不能丢，备份时必须同时保留 `hub.db` 和 `master.key`。

## 状态与派生

- **事件**：来源 + 事件编号去重；记录 `matched`、`routed`、`paused`、`refused`、`hops`，以及调度进度 `queued/running/creating/placed/replied/unassigned/failed`。
- **事项**：没有单独状态列，由同一 `rule + lane` 的轮次、卡片、复查和回执推导。
- **轮次**：`queued → claimed → done/nothing/cancelled`；领取后失联进入 `unknown`，迟到结果仍可接收。
- **卡片**：提问 `open → decided → done` 或 `open → closed`；通知通常 `open → closed`，FYI 创建即 `closed`。
- **阶段**：`kernel/stage.ts` 从最新轮次、卡片和回执只读推导，供 `board`、状态和续接判断共用。
- **决策与授权**：`decisions` 记录每个“事件 × 规则”为什么被接受或拒绝；`mandates` 只在真正派发时写入。
- **项目创建**：`project_creations` 记录调度提议、置信度、来源/类型、写入结果和错误；宿主负责配置持久化，内核不读写文件。

详细转换见 [state-machines.md](state-machines.md)。

## 四向插件

| 方向  | 入口                        | 连接方式                                      | 典型实现                                                                                          |
| ----- | --------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 来源  | `plugins/<name>/source.ts`  | 中台 HTTP Webhook 或外部程序调用 `/v1/events` | GitHub、GitLab、自定义 HMAC Webhook                                                               |
| Agent | `plugins/<name>/agent.ts`   | 接单程序启动本地进程                          | Claude Code、Codex、DSH、ZCode、命令模板、ACP                                                     |
| 通道  | `plugins/<name>/channel.ts` | 通道进程长轮询 `/v1/cards/next`               | 飞书、QQ（经 InSoulForge 机器人）、QQ 机器人直连、QQ（NapCat）直连、桌面通知、Webhook、自定义聊天 |
| 交付  | `plugins/delivery/`         | 普通 Agent 进程 + GitHub 状态                 | PR 审查、检查、合并、发布核对                                                                     |

插件查找顺序：`~/.agent-autoloop/plugins/<name>/<kind>.ts` 优先，其次内置 `plugins/<name>/<kind>.ts`。第三方插件必须自包含，只用 `node:` 模块和自己的文件；它加载时会执行，因此应视为可信代码。

## 单机与多机部署

### 单机

`agent-autoloop up` 在一个进程里启动中台、接单程序和配置中的通道。三者仍走 HTTP 协议，只是地址指向本机。默认监听 `127.0.0.1:3350`，不对外开放。

### 多机

- 一台机器运行中台（`hub`），可选运行通道；
- 其他机器通过 `join` 配置中台地址和 worker 密钥，只接活；
- 工作机不开放入站端口，由它主动长轮询；
- 中台前面放 HTTPS 反向代理，用于手机卡片和外部 Webhook；
- `rules.json` 中 Agent 的 `worker` 决定哪台机器接这条规则的活。

多项目目前是 `project / group / lane` 级隔离：可以按项目和事项并发、展示和路由，但不是多租户硬隔离。所有规则、密钥和事实仍在同一个中台数据库里。

调度 Agent 也遵守这个边界：快照只来自中台事实，模型不能凭记忆添加项目或节点；节点是否在线以 worker 心跳为准，项目落在哪台机器仍由 Agent 的 `worker` 决定，不另存节点表。它是外部任务和 Autoloop 内部路由之间的翻译层：外部只提交任务事实，调度负责选项目、选会话或直接回复；真正的授权、排队和状态仍由内核记录。

## 失败与恢复

| 场景           | 行为                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| Agent 进程崩溃 | 接单程序根据进程组和退出标记判断；未跑成的轮次按退避重试，最多 10 次   |
| 接单程序失联   | 心跳过期后轮次进入 `unknown`；工作机回来可继续报告；排队工作会提醒本人 |
| 中台进程被强杀 | 已提交事务不丢；未提交的决策视为未发生；重启复用投影或从日志重建       |
| 通道发送失败   | 按递增间隔重试，约一小时后放弃；卡片仍可在 `status` 中看到             |
| 规则文件写错   | 启动时拒绝启动并说明位置；运行中保留旧规则，并推一张卡片报告错误       |
| 回执格式错误   | 接单程序只让 Agent 重写最后一条消息，最多两次；不重做业务              |
| 事件循环       | 回执事件继承跳数，超过 8 层只记录不派发，并通知本人                    |
| 调度失败       | 事件记为 `failed`，同时生成未分配卡片；不无限重试，也不猜项目          |
| 调度越权       | 中台重新校验项目、来源、发送人、节点和置信度；模型只给建议             |

## 非目标

- 不提供 Web 管理界面；看板应由外部客户端读取 `/v1/state` 实现。
- 不内嵌模型调用；研判和预演都是普通 Agent 轮次。
- 不提供操作系统级沙箱；`access` 由各 Agent 插件翻译成 CLI 权限。
- 不提供多租户强隔离、计费或集中身份系统。
- 不自动修改 `rules.json`；规则由本人维护，运行时只记录规则版本。
