# 设计文档

本文说明 Agent Autoloop 的设计原则、核心模型，以及以 agent-autoloop 为轻量内核、吸收 Super-agent 治理概念后的取舍。实现落点见 [implementation.md](implementation.md)。

## 问题背景

三个参考项目代表三种取向：

| 项目           | 优势                                             | 代价                                          |
| -------------- | ------------------------------------------------ | --------------------------------------------- |
| agent-autoloop | 轻量、零运行时依赖、事件溯源、四向插件、单机可跑 | 早期缺少显式授权、研判和事项阶段              |
| Super-agent    | 授权、决定、事项和主动工作语义完整               | 依赖重、可变数据库、带 Web 面板，难以保持轻量 |
| Comma          | 常驻个人 Agent、多服务架构、会话化交互           | Elixir/OTP 与分布式多服务，部署和扩展成本高   |

融合选择是：**保留 autoloop 的骨骼和插件边界，把 Super-agent 的治理语义作为可选层加上去，不复制它的重依赖和面板。**

## 设计原则

### 继承自 autoloop

1. **注意力最贵。** 默认安静，只有规则要求先问、或确实需要本人解除阻塞时才打断。
2. **一切都是事件。** 外部系统、时间、到期复查、人的回答、手动运行都走同一套事件模型。
3. **一切都连进来。** 内核不主动连接外部；凭据留在使用它的插件或客户端。
4. **Agent 就是一个进程。** 给提示词，读最后一条消息；不要求 SDK。
5. **一轮不等人。** 要问人就结束这一轮；等待期间不占进程、不花 Token。
6. **规则才是指令。** 事件文字不能改变 Agent、目录、权限、通道或收件人。

### 融合新增

7. **治理可选。** 不配置 `policy` 时，行为与原来的 autoloop 一致；治理只收窄，不扩大权限。
8. **契约只加不改。** 新增字段都是可选的；旧配置、旧事件、旧插件不改也能运行。
9. **少概念。** 只引入 Policy、Mandate、Decision、Eval 和事项阶段，不造第五套工作流。
10. **事实优先。** 新概念都通过事实和投影表达，不写数据迁移。
11. **可解释。** 每个“为什么开始/为什么不开始”都能从 `decisions` 和 `why` 查到。

## 核心模型

### 事件

事件是系统唯一的外部输入形态：

```json
{
  "id": "issue-42-opened",
  "type": "issues.opened",
  "subject": "owner/repo#42",
  "summary": "一句话",
  "detail": "完整资料",
  "link": "https://example.com/42",
  "actor": "alice",
  "hops": 0
}
```

约束：

- `id` 在来源内唯一，用于去重；
- `type` 是匹配规则的稳定标识；
- `subject` 是事项分 lane 的依据；
- `summary`、`detail` 是资料，不进入提示词的指令部分；
- `link` 只允许 ASCII HTTP(S)；
- `actor` 用于来源级策略，不合法则留空；
- `hops` 表示处理链深度，超过 8 层不再派发。

### 事项、轮次与回执

- **事项**由 `rule + lane` 标识。`lane` 在规则写 `parallel` 时取事件 `subject`，否则为空。
- **轮次**是一次执行。一个事项可以有很多轮，一轮结束不代表事项结束。
- **回执**是 Agent 最后一条消息里的可选 JSON 块，用来提问、通知、结案、约复查、发事件、报告状态或提交研判结论。
- 回执在一个事务里一次生效；失败回执只允许通知，其他动作不生效。

### 卡片

卡片是唯一主动打断人的东西：

- `ask` 带 2–5 个选项，可附推荐项和 `about`；
- `notice` 是通知，可带 `fyi` 表示创建即结案；
- 卡片有版本和投递记录，通道可更新原消息；
- 回答只认第一次；回答会变成事件，让事项继续；
- 卡片链接是持有即授权，只应发给本人。

### 阶段

阶段是**只读派生**，不是新状态列。它从最新轮次、未结卡片、投递失败和回执报告计算：

| 阶段              | 含义                                  |
| ----------------- | ------------------------------------- |
| `person/answer`   | 有未回答的提问卡片                    |
| `person/review`   | 回执报告 `ready`，等人审阅            |
| `person/blocked`  | 回执报告 `blocked`，等人解除          |
| `person/failed`   | 回执报告 `failed`，等人处理           |
| `person/delivery` | 卡片投递失败，正在重试                |
| `working/queued`  | 有排队轮次或尚未开始                  |
| `working`         | 已领取、执行中，或回执报告 `progress` |
| `idle`            | 暂无动作，可能等复查或后续事件        |

`board`、`status`、卡片续接和阶段判断共用同一份 `stageOf`，避免各客户端说法不一致。

## Policy：谁可以让工作开始

`policy` 是全局开关，来源可以有更细的策略。

```jsonc
"policy": { "accept": "gate", "assessor": "claude", "fanout": true },
"sources": {
  "github": {
    "name": "GitHub",
    "adapter": "github",
    "policy": {
      "allowlist": ["alice"],
      "admission": "named",
      "bots": ["dependabot"]
    }
  }
}
```

### 三档接受模式

| 模式     | 行为                                          |
| -------- | --------------------------------------------- |
| `off`    | 来源密钥即授权；规则命中即派活                |
| `gate`   | 先做确定性检查，通过才记录授权并派活          |
| `assess` | gate 通过后再排一轮研判，研判 `accept` 才派活 |

默认是 `off`。只写 `policy.fanout` 不会自动开启 gate。

### 来源策略

- `allowlist`：允许发起工作的身份；空数组表示“来源自己放行的人都可以”，不是拒绝所有人。
- `admission: "named"`：事件必须在 `subject` 或 `summary` 中点名 Agent 的 id 或名称；`any` 不要求。
- `bots`：允许产生候选的机器人身份。机器人不受 `allowlist` 和 `admission` 限制，但仍需身份存在。

身份只在同一来源内比较，不同来源的账号不做映射。开启 Policy 后，空 `actor` 会被拒绝并记录原因 `no_actor`。

### 只收窄

治理层不能扩大规则权限：它只能让一个本来会派发的事件不派发，不能让规则匹配不到的事件被派发，也不能改变 Agent、目录、权限或通道。

## Decision 与 Mandate

### Decision

`decisions` 记录每个“事件 × 规则”的判断：

- `state`：`accept`、`stop`、`ignore`、`unavailable`；
- `reason`：为什么；
- `strength`：`explicit` 或 `inferred`；
- `scope`：做到哪一步；
- `rules_version`：当时的规则版本。

没有 Policy 时也会记录来源密钥接受的决定，因此审计链完整。

### Mandate

`mandates` 只在真正接下工作时写入，表示“凭什么可以开始这件事”。它记录事件、规则、强度、原因、范围和规则版本。研判 `accept` 后才写授权；如果事项正在等人处理，决定保留但不写授权、不派活。

### 与规则自发事件的关系

规则回执里发出的事件由该规则的 `emits` 授权，不再走来源 Policy，也不进研判。这是既有契约：规则作者已经通过 `emits` 明确声明该规则可以产生哪些事件。不要把它误读为“所有回执事件都免检”。

## Eval：研判轮

`accept: "assess"` 时，事件先进入一轮 `kind: "assess"` 的研判：

- 使用 `policy.assessor` 指定的 Agent；
- 强制下发 `access: "read"`；
- 提示词要求只判断、不做事、不改文件、不对外发消息；
- 最后一条消息提交 `verdict`；
- 只有 `accept` 才写决定、授权并排正式轮；
- `stop`、`ignore`、`unavailable` 只留决定；
- 研判取消、停止、规则删除或连续失败，事件记为 `unavailable`，规则记为 `refused`，不会永久挂起。

研判是普通 Agent 轮次，不是内嵌模型调用。因此它遵守“一切都连进来”和“零运行时依赖”，但也意味着 `command` 类 Agent 的只读性取决于其程序本身，不是内核沙箱。

## Dispatch：调度 Agent

调度 Agent 解决的是“事件没有命中规则，但人希望它自己找到项目”的问题。它不是第二个工作流，也不替 Agent 干活，而是**控制面的一轮只读判断**：

1. 外部事件先按规则做确定性匹配；通知、回答、定时和手动运行不算任务，不进入调度；
2. 没有匹配时，先尝试项目的 `when.subjects` 和 `aliases`；
3. 仍然无法放置，且配置了 `policy.dispatch` 时，排一轮 `kind: "dispatch"`；
4. 调度 Agent 从**中台事实快照**里读项目说明、节点、在线状态、活跃事项、最近轮次、可续会话和本人纠正偏好；
5. 它是任务和 Autoloop 之间的翻译层：任务返回 `route`；不是任务的聊天可以返回带 `fyi` 的 `notice` 直接回复。它不执行代码、不改文件、不发消息；
6. 中台重新校验项目、来源、发送人、节点、事项阶段和置信度；
7. 通过后走与普通事件相同的 `dispatch()`，写决定、`routed`、授权和扇出；项目未知时不再伪造项目 lane。

关键取舍：

- **模型不做授权。** `route` 是建议，不是权限；最终能否派活只由中台事实决定。
- **确定性优先。** 别名和 `subjects` 能确定的路由不花模型 Token；只有真正未分配的事件才询问。
- **外部只描述任务。** 外部系统不需要知道规则、目录、节点和会话；调度 Agent 把自然语言任务翻译成合法的项目、会话和 `route`，把非任务聊天直接答回去。
- **一事件一轮。** 每个未分配事件独立成轮，避免多个事件合并后只处理第一个，保持可审计、可重试。
- **只读控制面。** 调度轮强制 `access: "read"`；它没有 `thread`，不能把虚构的事项引用带回模型。
- **失败不悬挂，也不伪装。** 调度失败、无 `route`、低置信度或不合法项目都会落成“未分配”卡片，不会无限重试；失败本身仍保留为 `dispatch_state: "failed"`。
- **会话隔离。** `continue` 只续同项目、同 lane、同 Agent、且没有被其他 queued/claimed/unknown 轮次占用的会话；否则安全新开，绝不把两个任务塞进一个可能仍在运行的会话。
- **回复可追溯。** 调度成功、直接回复和未分配卡片都继承原事件的 `reply`，私聊回私聊、群聊回原群。
- **不绕过人的阻塞。** 项目在 `person/blocked` 或 `person/failed` 时，调度和别名都不能强行塞入新工作；候选项目和最终放置会同时检查原始会话 lane 与项目 lane，避免调度后的 `<会话>/<项目>` 被漏看。

默认关闭。没有 `policy.dispatch` 时，未匹配事件只记录，行为与旧版本完全一致。这样调度是可选治理层，不是 autoloop 的新核心依赖。

### 项目管理属于中台控制面

项目登记是**配置写入**，不是一次任务执行，也不属于 InSoulForge 插件：

- 唯一实现放在 `host/projects.ts`；CLI 和 owner-only HTTP 接口都调用它，不各写一套校验；
- 它同时校验 `rules.json` 和可选的 Activity `projects` 清单，再原子写入；任一文件不合法就都不写；
- HTTP 接口不允许传 `activityConfig`，因此远程调用不能借请求写任意文件；
- 调度 Agent、任务 Agent 和插件都不能直接改 `rules.json`。调度 Agent 只能在策略允许时**提议**新建项目；中台校验后生成 `project_creations` 待办，由宿主写入配置；
- 项目登记成功后立即重载规则，新增和删除都无需重启中台；Activity 服务自行监听配置变更并重连注册。

这条边界让“模型判断项目”和“系统承认项目”保持分离：模型给建议，中台做授权和持久化。

### Phase 2：自动创建项目

自动创建是显式开启的可选能力，默认关闭：

- `policy.dispatch.create: true` 才允许调度 Agent 提交 `create`；
- `create.confidence` 必填，低于 `minConfidence` 直接拒绝；
- 项目名不能与现有项目重复，同一项目不能同时有多份待写入提议；
- `workers` 是节点白名单；提议省略 `worker`/`agent` 时，中台仍按宿主最终选择校验，不能靠省略字段绕过；
- 目录必须是绝对目录；Agent 和节点必须已登记；
- `create` 不能和 `route`、`ask`、`resolve`、`later`、`events` 混用；
- 内核只记录提议，不读写配置；宿主在事实提交后调用 `host/projects.ts` 原子写入；
- 新规则继承事件的来源和类型，不会把所有自动项目固定成 QQ；
- 写入成功后事件重新调度；失败则记录错误、回到未分配卡片，不留下永久 pending；
- `project_creations` 和 `/v1/state.projectCreations` 保留提议、结果、错误和时间，供审计与回滚定位。

自动创建仍不自动迁移目录、不自动改已有项目规则、不自动删除项目。需要这些操作时，走显式 CLI 或 owner-only 管理接口。

## 预演：speculate

规则写 `"speculate": true` 时：

1. 事件先排一轮 `kind: "speculate"` 的后台预演；
2. 预演强制 `read`，提示词要求先试、不值得交付就安静收尾；
3. 只有 `outcome === "done"` 且回执 `report.state` 为 `ready` 或 `progress` 时，才把同一批事件排成正式一轮；
4. 正式一轮才补授权、`routed` 和扇出；
5. 预演没有找到值得交付的东西时，只留记录，不发卡片、不通知、不产生后续轮。

预演适合“先查一下有没有问题，有再叫人”的巡检类任务。它不改变正式轮的执行权限，只减少无效打扰。

## 扇出：fanout

`policy.fanout: true` 时，一个事件真正派发给某条规则后，也会作为**上下文**送到同一 `subject` 上其他活事项：

- 只提供资料，不授予权限；
- 不改变其他规则的决定或授权；
- 回答不扇出，它是原事项的私有输入；
- 研判只结算真正接下的事件，不把扇出上下文当授权依据；
- 扇出发生在真正派发之后，预演阶段不扇出。

扇出适合多项目协作：一个事项的进展可以让相关事项看到，但不会让它们自动获得执行权。

## 线程召回

`Job.thread` 给 Agent 稳定引用：

```json
{
  "id": "处理 issue:owner/repo#42",
  "rule": "处理 issue",
  "lane": "owner/repo#42",
  "project": "app",
  "rounds": [{ "run": 7, "state": "done", "summary": "查过了", "at": "..." }],
  "related": [{ "rule": "告警", "lane": "owner/repo#42", "stage": "working" }]
}
```

提示词只列最近几轮和同对象上其他活事项，不展开全文；需要细节时 Agent 用 `agent-autoloop why <轮次>` 查。这样长历史不会每轮都塞进上下文。

## 多项目

`project` 是命名和分组简写，不是运行时隔离：

- 未写 `group` 时，`group` 取 `project`；
- 未写 `cwd` 时，`cwd` 派生为 `~/<project>`；
- `board` 和状态按项目展示；
- 真正的并发仍由 `group`、`parallel`、`maxActive` 和 `worker.capacity` 决定。

多个不相关项目可以共享一个中台，用不同 `project`、`group` 和 `cwd` 分开；但它们共享同一个数据库、密钥体系和事实日志，不是多租户硬隔离。

## 通道输出风格

通道可声明 `style`：

- `im`：短消息，先说结论，不贴代码、文件、日志；
- `async`：完整交付，写背景、改动、验证，可分小节，可带代码和链接。

规则未指定通道时使用 `defaultChannels`；风格取第一个声明了 `style` 的通道。风格只影响提示词，不改变卡片内容或投递逻辑。

## 兼容与演进

- 新字段全部可选；旧配置不写时行为不变；
- 旧事件没有 `actor`、`hops` 时按空值和 0 读取；
- 旧插件不认识新字段时忽略即可；
- 状态投影可从事实日志重建，不写迁移；
- `/v1` 路径和字段语义的破坏性变更才升主协议版本；
- 新增能力优先用新字段、新事件类型和新投影表达。

## 已知取舍

- **轻量优先于完整平台化。** 没有 Web 面板、多租户、集中身份和计费。
- **插件信任优先于强隔离。** 插件是本地代码，加载即执行；需要隔离时用系统账号或容器。
- **提示词约束优先于系统沙箱。** 研判和预演的只读性主要靠 `access` 和提示词；`command` 类 Agent 需自行保证。
- **单库优先于分布式。** 多机可以接活，但中台仍是一个 SQLite 事实库；没有跨库复制或高可用集群。
- **审计优先于自动修复。** 被 Policy 拒绝的事件会记录，不会自动重试或猜测意图。

## 与其他项目的关系

本设计不是把 Super-agent 整体移植进来，而是：

- 采用它的授权、决定、事项阶段和主动研判语义；
- 用只读调度 Agent 补上“未匹配事件如何找项目”，但模型只给建议，中台保留最终授权；
- 保留 autoloop 的事件、轮次、回执、卡片和插件模型；
- 用普通 Agent 轮次实现研判和预演，避免新增模型 SDK；
- 用配置和投影实现治理，避免新增运行时依赖和数据库迁移；
- 不引入 Web 面板、分布式服务和重依赖。

Comma 的常驻会话和多服务思路没有直接落地；当前架构通过通道、MCP 和外部客户端提供交互，不内置常驻对话服务。
